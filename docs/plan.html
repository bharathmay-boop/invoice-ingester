Stack

Next.js App Router on Vercel, Postgres on Neon through the Vercel integration, Vercel Blob for the original files, and the pg_trgm extension for item matching. Extraction goes through the Anthropic TypeScript SDK or the OpenRouter HTTP API depending on the setting.

Item matching lives in Postgres rather than in application code. Trigram similarity is a built in index type, so the matching logic is a query with a threshold rather than a library and a scoring function. That is one less dependency and one fewer thing to get wrong.

03Architecture

Four moving parts and one shared schema holding them together.

Figure 2, request path for a single invoice

The shape worth noticing: both providers are behind one function that returns one type, and everything downstream of validate.ts has no idea which model produced the data. Swapping providers cannot break the review screen, the matcher, or the database, because they never see a provider specific response.

UNIQUE (vendor_id, invoice_number)

Upload the same invoice twice and the database refuses it. Duplicate detection is a constraint, not a feature you have to remember to build or a heuristic that gets it wrong.

line_item.item_id is nullable

An unmatched line still saves. It just does not appear in price history yet. Nothing about ingestion ever waits on matching, which keeps the two flows independent.

raw_description is never overwritten. Matching adds a link, it does not rewrite what the vendor actually printed. If a match turns out to be wrong later, unlinking restores the truth with nothing lost.

extraction_meta holds the provider, the model id, the token counts and the raw response. It costs nothing to store and it is the only way to answer questions like whether one model reads a particular vendor's layout better than another.

05Extraction and the provider layer

One schema, two callers, no provider specific code past the boundary.

Four files, and the last one is the only one either provider gets to disagree about:

lib/extract/schema.ts      the JSON schema plus a zod parse, shared by both
lib/extract/anthropic.ts   Anthropic SDK, claude-opus-5, strict tool schema
lib/extract/openrouter.ts  OpenRouter HTTP, response_format json_schema
lib/extract/index.ts       reads settings, calls one of the two, returns one type

Both paths return the same object and both run through the same zod parse before anything touches the database. That is what keeps this cheap: adding the second provider is one file and a branch, not a second pipeline.

Claude path

Anthropic TypeScript SDK, model claude-opus-5, adaptive thinking, and a tool definition with strict: true so the returned arguments are guaranteed to validate against the schema. PDFs go as a document content block and images as an image block. Roughly two to four cents per invoice.

OpenRouter path

OpenAI compatible endpoint with response_format set to a json_schema, using the model id chosen in settings. Cost varies by model, which is most of the reason to have this option at all.

The model dropdown

Checked before writing this

OpenRouter's GET /api/v1/models returns, for every model, an architecture.input_modalities array and a supported_parameters array. That means the app can work out which models can actually read an invoice and return structured JSON, rather than us maintaining a list by hand.

So the dropdown is built at runtime, not hardcoded:

  1. Fetch the catalogue server side, cache it for 24 hours.
  2. Keep only models whose input_modalities includes image and whose supported_parameters includes structured_outputs. Everything else would fail at extraction time with a confusing error.
  3. Order by a short RECOMMENDED array in code, then by price for the rest.
  4. Show the top ten. Two carry a Recommended badge and one line saying why.

Why not a fixed top ten: model ids on OpenRouter change often, and a pinned list rots within weeks. A dead id in a dropdown does not fail when you pick it, it fails later when you upload, which is the worst place to find out. Filtering live means the list is always models that exist and can do the job. The only curated part is which two get the badge, which is one array to edit.

Known ceiling

If OpenRouter is unreachable the app falls back to the last cached list, and if there is no cache it says so and asks you to retry rather than showing an empty dropdown. The two recommended ids are matched by string, so if one is retired it simply loses its badge instead of breaking the page.

Catching a bad extraction without reading every invoice

Two arithmetic checks run before anything saves:

  1. Line item amounts sum to the subtotal.
  2. Subtotal plus CGST plus SGST plus IGST equals the total.

Both within a one rupee tolerance for rounding, which is configurable. Fail either and the invoice saves with status needs_review and the failing figures highlighted, instead of confirmed.

This is the highest value code in the build relative to its size. A model that quietly invents a number is worse than one that fails loudly, because a wrong total flows straight into your spend figures and nothing ever tells you. Arithmetic catches that class of error for free, without a human checking every line.

How keys are handled

Keys are entered here and encrypted at rest with AES-256-GCM, using a master key held in a Vercel environment variable rather than in the database. Once saved, a key is never sent back to the browser. The field shows a masked form with the last four characters only, and the sole action available is Replace. Test connection makes one cheap call and reports pass or fail, it never echoes the key back. The public read only view does not render this page at all, and the API routes behind it reject any request without the session cookie.

The two matching thresholds are on this page on purpose. Where they should sit depends on how varied your actual invoices are, and that is not knowable before there is real data in the system. Leaving them adjustable is cheaper than guessing right, and it is the difference between a demo and something you would keep using.

Flow B, matching

Figure 4, how a line item finds its catalogue entry

Vendors skip all of this. GSTIN is a real unique business identifier, so vendor identity is an exact key lookup. Only invoices with no GSTIN printed fall back to a normalised name comparison, and those surface on the review screen for you to confirm rather than being guessed at.

Normalisation is the unglamorous part that decides how well the rest works: lowercase, strip punctuation and pack sizes and units, drop filler words like "pack of" and "approx". It gets its own tests because it is the one piece where a small change quietly shifts every score in the system.

Why contracts wait

Contract variance is the most valuable thing this product could eventually do, and it is entirely unbuildable until invoices, vendors and items are reliable. A variance check on top of shaky extraction produces confident wrong answers, which is worse than no check. The v1 data model already has room for it: contracts attach to a vendor and reference catalogue items, both of which exist from day one, so nothing needs reshaping later.

09Scope and testing

Deliberately not in version one

Multiple users

No sign up, no accounts. One password gates edits.

Separate OCR

Vision models read scans directly. A second pipeline buys nothing.

Price alerts

Needs a baseline of real history first. Version 2.

Contracts

Specced above, deliberately last.

Bulk queues

Upload several at once is enough. Hundreds is a problem you do not have.

Accounting export

CSV out covers it. Tally and Zoho integrations are their own project.

Tests

One test file, covering the three pieces of logic where a silent mistake would not announce itself:

  • Normalisation, because every match score depends on it.
  • Match thresholds, that the three bands behave at their boundaries.
  • Arithmetic validation, including the rounding tolerance and each tax combination.

Everything else is a page rendering or a database query, and those fail loudly on their own. No framework, no fixtures, no test per function.

Open questions, none blocking

  • Which two OpenRouter models get the Recommended badge. Best answered by running the same ten invoices through the shortlist once extraction works, rather than by picking now.
  • Whether the public demo should let a visitor upload their own invoice. It is the better demo and it spends your API credit, so it is a flag, defaulted off.
